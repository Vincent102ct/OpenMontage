# P2.1 — Studio → Story Intake Bridge

Status: accepted 2026-10-22 on the reported test and browser acceptance evidence; committed on `coding`.
P2.2 not started.
Baseline: `coding` at `b4c3c47` (P1 accepted).

Story Intake turns a saved Studio **Full story** request into reviewable,
source-linked draft artifacts. It is user-triggered (**Prepare Story Draft** in
Studio, or one CLI command) and runs intake only: no research, TTS, asset
generation, rendering, model or network call. Every result stays
**pending human review**; nothing is approved automatically.

Windows usage: [STUDIO_WINDOWS.md](../STUDIO_WINDOWS.md#prepare-a-story-draft).

## Flow

1. Validate the project ID (P1 rules) and load the request through
   `ProductionStore.detail()` (schema, path and byte checks).
2. Re-read and re-validate the exact request and story bytes used, compare the
   story with the recorded content and SHA-256, and require
   `style=stickman_horror_2d`, `review_mode=human_required`,
   `publishing_enabled=false`, `status=production_not_started`.
3. `input_mode=story` only. Topic and canonical requests are refused with
   `unsupported_input_mode` and a clear message; they never fall through to story mode.
4. Derive outputs deterministically, write them to a temporary folder, then
   publish atomically with one directory rename.

`production_request.json`, `input/story.md` and `project.json` are never written.

## Outputs — `projects/<id>/artifacts/story_intake/v1/`

| File | Content |
| --- | --- |
| `story_intake_report.json` | Status, review state (`pending_human_review`, not approved), formats, style, coverage, counts, canonical-compatibility assessment, checkpoint decision, SHA-256 of every other output |
| `story_segments.json` | Paragraph segments (`SEG_0001`…) with exact text, char and byte spans, line numbers, per-segment SHA-256, kind (heading / paragraph / dialogue_line / emphasized_line) and linked proposed-change IDs |
| `story_inventory.json` | Candidate characters, locations, objects, motifs (time expressions, numbers, repeated lines and phrases), quoted dialogue, emphasized text, narrative-event candidates, questions for human interpretation and excluded candidates with reasons |
| `working_text_proposal.md` | The original bytes with every proposed removal applied, for preview only |
| `working_text_changes.json` | Each proposed change: rule, rationale, confidence, exact source span (char and byte), removed text, before/after excerpts, `status: proposed`, `approved: false`; plus observations with no change proposed |

Every JSON output carries the same `provenance` block: project ID, request path
and SHA-256, source path, SHA-256, bytes, characters, line endings, NFC status,
and intake version. Outputs contain no timestamps except the report's
`created_at`, so identical request bytes produce identical artifacts.

The folder is a subdirectory of `artifacts/`, so Backlot (which reads only
top-level `artifacts/*.json`) and the pipeline do not treat it as stage output.

### Repeat runs, conflicts and failures

| Situation | Result |
| --- | --- |
| First run | `201 created` |
| Re-run with unchanged inputs | `200 already_prepared`; existing files verified and returned, not rewritten |
| Concurrent runs | One publishes; the others return `already_prepared` |
| Existing output edited, partial, or the request or story changed after intake | `409 existing_output_invalid`; nothing is overwritten. Move `story_intake/v1` aside to re-run |
| Story file changed or missing | `409 source_mismatch` |
| Invalid request / unsafe ID / missing project | `422 invalid_request` / `422 invalid_project_id` / `404 not_found` |

## Editorial proposals (never applied to the original)

Generic, rule-based and shown with exact spans:

- `stray_line_end_backslash` (high confidence): a Markdown line-break backslash
  before a blank line or end of text. Only the backslash and the spaces before it.
- `trailing_meta_note` (medium confidence): the last paragraph, set apart by two
  or more blank lines, at most 200 characters, and referring to the story and its
  author (for example *câu chuyện* together with *tôi*). Removes the note and the gap before it.
- Observations only (no change proposed): extra blank lines; a final paragraph
  after a large gap without the note signals.

Nothing else is rewritten or normalized (CRLF, punctuation, spacing and Unicode stay as written).

## Analysis coverage — incomplete by design

Deterministic:
- Segmentation.
- Rule-based candidates from `tools.story.story_analyzer.RuleAnalyzer`, the M1 closed vocabulary.
- An intake list of role references (`bà chủ`, `người mẹ`, `con bé`…).
- Numbered places (`phòng 407`).
- Time expressions (`2:17`, `2 giờ 17 phút`, and spelled hours only with a time word).
- Numbers, repeated lines and phrases.
- Quoted and emphasized text.
- Reporting markers.

Deliberately **not** reused from the analyzer, because it invents these values:
- Fallback gender, age and color.
- Default `room` location.
- Dialogue speaker attribution.

Candidates that only appear as a standalone one-word line (sounds such as *Cốc.*,
*Lộp.*) are listed in `excluded_candidates` with the reason.

Semantic analysis is `not_performed`: no Ollama or other model is used. Plot,
twists, contradictions, coreference and speakers are turned into explicit
review questions instead of guessed answers. Ollama-assisted analysis remains
optional future work and must stay non-authoritative.

## Canonical compatibility (fiction vs Master Story Package)

The historical schema cannot hold this fiction without fabrication:
- `case.year` needs an integer, but the story states none.
- `sources[]` verification has no meaning for user-authored fiction.
- `claims[].status` values (DOCUMENTED_FACT…LEGEND) describe historical evidence.
- `timeline[].date_start` needs dates, but the story uses relative time.

Recommendation for P2.2 is the smallest compatible extension: a **separate fiction
story package variant** with its own schema and validator. It would:
- Replace case, sources, claims and timeline with three things:
  - authorship provenance, i.e. this intake's source hash;
  - in-story canon facts with fiction statuses (for example `author_stated`, `character_claim`, `ambiguous`);
  - relative event order.
- Reuse entities, continuity rules, narrative segments and Short/Long format plans.

`lib/master_story.py`, the historical schema and STORY 053 stay unchanged.

## Checkpoints

No checkpoint is written. The `character-animation` manifest has no intake
stage, and writing `research`/`proposal` checkpoints would claim stage work that
did not happen. Integration options:
- add an explicit intake/story stage to the manifest, or
- have P2.2 consume `artifacts/story_intake/v1/` as reviewed input.

## Interfaces

- Studio: My Productions → **Prepare Story Draft**. The button is disabled with an
  explanation for Topic and Canonical. The draft panel shows:
  - review status and coverage warning;
  - counts;
  - proposed changes with before/after;
  - questions;
  - candidates;
  - saved files.

  Opening Studio or the list never triggers intake.
- API:
  - `POST /studio/api/productions/{id}/intake` (same-origin JSON only).
  - `GET /studio/api/productions/{id}/intake` (verified read).
  - `GET /studio/api/productions` adds `intake_status`.
- CLI: `.\.venv\Scripts\python.exe -m studio intake <project-id>`.
- Backlot is unchanged and stays read-only.
