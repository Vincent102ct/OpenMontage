## Canon and design are separate

Only the **current**, explicitly approved P2.3 Reviewed Fiction Story Package is
eligible. `studio.reviewed.read_reviewed_story` re-verifies original source and
request, intake/fiction artifacts, append-only decision history, all reviewed
versions and the separate `preproduction_story_only` approval. `ready_for_next_stage`
must be true and blockers empty. Neither an unapproved draft nor an older approval
whose decisions/inputs are no longer current can prepare a Visual Bible.

The new contract never writes story text, events, facts/claims, relationships,
dialogue, uncertainty, original/private Story Bible or existing approvals. Canonical
IDs and evidence are read-only provenance. Appearance, casting, environment,
lighting and prop selections are explicitly **creative proposals, not canonical
physical facts**, requiring visual review. No gender, age or costume is inferred
as a story fact from a library asset description.

## Contract and persistence

Schema: `schemas/story/story_visual_bible.schema.json`, version `1.0`.
Compiler/validation: `lib/story_visual_bible.py`.
Storage: `studio/visual_bible.py`, reusing P2.3 `review_lock`, `safe_review_path`,
`write_once`, integrity hashing and atomic folder publication.

`artifacts/story_visual_bible/v1/`, then v2, v3, …:

| File | Contents |
| --- | --- |
| `visual_bible.json` | Immutable candidate: project/version, exact canonical input pins, library pin, cast/appearance, location/lighting/geometry/anchors, persistent props, continuity/ambiguity, shared Short/Long identity digests, unresolved decisions and blockers. |
| `manifest.json` | Exact input/library hashes, structured choices, package byte hash, previous manifest hash and timestamp. |
| `approval.json` | Added once by a separate explicit action; exact displayed package/manifest hashes, reviewer/time, integrity checksum and `scene_planning_only` scope. |

Canonical input pins include reviewed version, source/working-text hashes, package
and manifest hashes, approval **file** hash and ordered decision-history digest.
Library `openmontage.cinematic_cartoon_horror@p3.2a.1` pins the entire 18-asset
manifest; selected assets also carry `{kind,id,revision,sha256}`. Revisions must be
positive integers. P3.2A verifies stored revision fingerprints and returns defensive
copies; missing/modified revisions fail rather than upgrade silently.
The current adapter requires that exact whole-library manifest, not only the
selected assets. Adding assets/revisions or changing the library version needs a
separately scoped compatibility decision; existing candidates are not migrated.

Package `review_status` remains `pending_explicit_visual_approval`: immutable
content cannot approve itself. Only a verified separate approval makes the view
`approved_for_scene_planning`. Readiness additionally requires the latest visual
version and exact current approved canon. Changing approved choices creates a new
version and requires new approval. Repeating identical preparation/approval is
idempotent. GET views/handoff do not write files. Missing/tampered history, content,
manifest or approval is refused without overwriting evidence.

Contracts contain IDs and hashes, not absolute Windows paths. Rendering workspaces
may contain machine-local paths; they are ignored derivatives, never canonical
contracts. These hashes follow the existing local integrity model, not signatures
against an attacker able to replace every application file and checksum.

## Binding and continuity rules

- Character suggestions consume distinct existing identities in canonical order.
  They remain unreviewed proposals. Extra roles stay explicitly unbound; the same
  identity cannot silently play unrelated roles. Full appearance data comes only
  from its pinned asset, with no arbitrary outfit/per-format overrides.
- Locations start unassigned; compatible environments/lighting require an explicit
  selection and acknowledgement. Geometry comes from the existing P3.2A resolver,
  preserving floor, walk range, doors, windows, fixtures, presence clips and props.
  Missing assets/features or incompatible lighting create blockers, never a P3.1
  demo-room fallback.
- Every canonical object requires a supported prop and a real environment anchor.
  Canonical prop location is preserved. Supported anchors are door handles, window
  centres and lamp bulbs, derived from the existing environment geometry. Other
  prop types stay blocked until compatible assets exist. If P2.3 omitted its
  optional location, the location is an explicit visual decision. Moving props
  that require more than one location/anchor state remain blocked in this version.
- Both formats carry identical character appearance and environment digests.
  Canonical continuity rules/intentional ambiguities are copied read-only and
  require acknowledgement. Shot pacing/framing is a future planner concern.
- Unknown/unshown identities default to unseen. Only a canonical **partial**
  character may explicitly receive a silhouette; any location presence must cite
  that character and a location where it participates in canonical events, plus
  a valid environment presence anchor. Horror genre alone adds no figure.
- Schema/structural checks cannot judge cinematic quality or whether a creative
  choice semantically fits every story detail. Humans review those choices.

## Studio workflow

Use **My Productions → Visual Bible** (or the section below Story Review).

1. Materialize and explicitly approve current Reviewed Story content using P2.3.
2. Choose **Prepare Visual Bible**. This saves an unapproved immutable candidate.
3. Inspect candidate IDs/revisions, summaries, appearance, palettes, anchors,
   provenance, limitations and blockers. Change representation/casting,
   environment/lighting/flicker, props/anchors or optional canonical partial presence.
4. Acknowledge each creative proposal and shared continuity. **Save new visual
   version** preserves previous versions. Changing a selection clears its review.
5. **Preview reference visuals** renders local PNGs through the existing
   `character_rig_renderer → StoryVideo / shared IK → Remotion renderStill`.
   The synthetic proof has two poses per character per environment plus empty
   environment references. No MP4, TTS, Foley, production checkpoint or publishing.
6. After all blockers are resolved, acknowledge the separate approval statement
   and choose **Approve Visual Bible**. The POST pins both exact displayed hashes.
   Reloaded or newer canon/design invalidates old tabs and readiness.

JSON editing/Codex is not required for this normal review flow. JSON import of an
authored **story-content** draft remains the existing P2.2 entry, outside visual
design authoring. No Backlot source changes. Existing local-origin JSON/size
checks, trusted local hosts, escaping, path/reparse guards and shared write lock
apply to new routes. Preview image filenames and content hashes are verified.

Reference previews need installed Node, Chrome and Remotion; nothing is downloaded.
Unavailable rendering returns a clear error; text/palette review remains possible.
References are cached under `assets/visual_bible_refs/<digest>/` using exact visual
hashes and renderer-source hashes. They never overwrite a prior version or preview.
The batch limit is 40 reference PNGs. Generated workspaces/media remain ignored.

## API and future P3.4 interface

Under `/studio/api/productions/{id}`:

| Request | Result |
| --- | --- |
| GET `/visual-bible`, `/visual-bible/{version}` | Verified latest/historical view; readiness is computed. |
| POST `/visual-bible` with `{}` | Prepare current eligible canon; no approval. |
| POST `/visual-bible` with base version + displayed hashes + structured choices | Save a new immutable candidate; reject stale base. |
| POST `/visual-bible/{version}/approve` | Separate explicit scene-planning approval for exact displayed hashes. |
| POST `/visual-bible/{version}/references` | Explicit local reference PNG batch for displayed hashes. |
| GET `/visual-bible/references/{key}/{name}` | Verified PNG from the current candidate only. |
| GET `/visual-bible/handoff` | Current approved visual handoff; otherwise refuse. |

GET `/studio/api/visual-assets` provides pinned candidates, environment anchors,
supported prop anchors and known limitations. Error codes distinguish canonical
not ready, invalid binding/version, stale visual, blocked approval, integrity
failure and unavailable reference renderer.

`scene_planning_handoff(store, project_id)` is the small P3.4 interface: canonical
character/location IDs to pinned appearances/environments/lighting, persistent
prop/interaction data, approved continuity, library/canon/visual versions and
hashes. Consumers must use this verified function at handoff time, not trust a
cached JSON's approval flag. The planner itself is not implemented.

Fiction is the only input adapter in this version. A future historical adapter can
supply a separately verified canonical reference, but this task does not invent
historical approval semantics, alter Master Story schemas or touch STORY 053.
