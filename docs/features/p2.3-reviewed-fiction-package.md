# P2.3 — Reviewed Fiction Story Package

Accepted on 2026-10-23 for scoped publication on `coding`, based on automated
and real-Chrome evidence. Baseline: `dd59f7c1816059a6cdcc30774a92122e0b6802ed`.
Acceptance covers the implementation only. The real story has not received
semantic approval; no private draft is imported and no production is started.

P2.3 materializes recorded editorial choices into immutable reviewed content,
then offers a separate **Approve Reviewed Story** action. Approval covers
pre-production story content only. TTS, animation, rendering, checkpoints,
provider calls and publishing are outside this feature.

## Contract and storage

Inputs are the verified original story and request, P2.1 intake, P2.2 fiction
draft and verified append-only decision log. P1/v1 inputs are never written.
Historical STORY 053 artifacts and contracts are unchanged.

`artifacts/reviewed_fiction/v2/` (then `v3`, `v4`, …):

| File | Contract |
| --- | --- |
| `reviewed_package.json` | Immutable candidate: original source hash, reviewed working text/hash, complete character-offset mapping, per-target dispositions, retained canonical items and formats, explicit questions and blockers. |
| `reviewed_working_text.md` | Exact UTF-8 text after accepted intake removals only. Original CRLF and Unicode are preserved. |
| `manifest.json` | Every source/request/intake/v1 file hash, ordered decision IDs and raw file hashes, applied dispositions, output hashes and version. |
| `approval.json` | Added once after explicit approval: exact package + manifest hashes, version, reviewer, timestamp, integrity hash, `approval_scope: preproduction_story_only`, production and publishing disabled. |

Candidates, including blocked candidates, are immutable. Repeating materialization
with identical inputs and decisions returns `already_materialized`. Changing a
decision creates the next version; it never rewrites the previous one. Repeating
the same approval returns `already_approved`. GET requests write nothing.

The candidate's `canonical_story.approved` and each format's `approved` stay
false: a content file cannot approve itself. Only a verified separate approval
record makes the returned view `approved_for_preproduction`. Consumers must use
the verified view's `ready_for_next_stage`, which also requires current inputs
and decisions. An old approved version stays frozen history when decisions change;
it is no longer the current next-stage handoff. Neither status authorizes production
or publication by itself.

## Materialization rules

- **Edits:** Accept removes exactly the proposed original span; Reject keeps its
  text; Defer/undecided/stale blocks approval. Original evidence is retained as
  source history, with a complete source-to-working mapping (retained and removed
  ranges). Offsets count Unicode characters; hashes cover exact UTF-8 bytes.
- **Semantic items:** only Accept materializes an item as canon. Reject excludes
  that interpretation, not the original story text. Defer remains unapproved and
  blocks approval. References to excluded identities, locations, props, facts,
  events, sounds or continuity items are reported, never silently repaired.
- **Questions:** Answer records a human interpretation, not an inferred factual
  rewrite. **Preserve Ambiguity** records `preserve_ambiguity` in the same append-only
  history, with no answer. Its canonical ambiguity is `intentionally_unresolved`.
  Defer never has that meaning. Unknown attribution requires an explicitly reviewed
  linked ambiguity; no speaker is fabricated.
- **Formats:** both accepted plans derive from the same reviewed canon. Short is
  9:16, Long 16:9. Original narration references remain intact; `working_spans`
  map every cited range into the approved working text. Verbatim narration is
  reconstructed from those mapped spans only. Authored proposals keep their exact
  explicitly accepted wording and source links; changed/removed support blocks
  approval instead of triggering a rewrite.
- **Coverage:** the existing validator checks shared IDs, evidence, claims vs
  later revelations, source order, exclusions and duration arithmetic. Added
  checks cover sound references, Short source/sound inclusion in Long and every
  retained non-whitespace character of the Long story body. A rejected exclusion
  cannot silently remove approved story text.

The existing v1 validator is reused through a temporary in-memory draft-state
projection, preserving the original canonical v1 schema. Reviewed status and
narration mapping are separate v2 concerns. Original source segments/evidence
are immutable archival evidence; reviewed narration uses the reviewed working
text. Duration remains an estimate, never a measured audio result.

## Integrity and explicit approval

The UI presents the candidate version, both hashes, applied changes and accepted/
rejected items, intentionally unresolved questions, both narration plans and
remaining blockers. The approval button requires a separate acknowledgement and
is unavailable while blockers or stale decisions remain.

The server independently re-verifies inputs, decision prefix, derived content,
manifest and blockers before writing approval. The browser submits both exact
displayed hashes. Newer decisions or mismatched hashes produce `stale_reviewed`;
blockers produce `approval_blocked`. Each error explains the reason.

Writes to decisions/materializations/approvals share an exclusive local lock.
Complete files publish atomically without replacement; complete version folders
publish via rename. Review paths reject symlinks/junctions and escapes. New
decision records include an integrity checksum, including the final entry.
Existing P2.2 records remain readable; manifests pin their exact file bytes too.
These are local integrity checks, not cryptographic proof against an attacker
who can rewrite all application files and checksums.

If a process is terminated while holding `.write-lock`, subsequent writes refuse
to proceed. After verifying no review writer is running, inspect and retire the
stale lock locally; never delete an active lock or edit an approved artifact.
Damaged inputs, history, versions or output hashes are refused without overwrite.

## API

All POSTs require local-origin JSON, using the existing Studio protections.

| Method/path under `/studio/api/productions/{id}` | Effect |
| --- | --- |
| POST `/review/decisions` with `preserve_ambiguity` | Explicit question disposition; append only. |
| GET `/reviewed-story` | Latest verified view + version list, or `state: missing`. |
| GET `/reviewed-story/{version}` | Verify and inspect a frozen historical version. |
| POST `/reviewed-story` with `{}` | Materialize current verified decisions; no approval. |
| POST `/reviewed-story/{version}/approve` | Requires `package_sha256` + `manifest_sha256`; explicit pre-production content approval only. |

dialogue, a reported claim and later conflicting writing, relative time, clicks,

## Next-stage blockers

- Human semantic review remains authoritative. Structural checks cannot prove
  that a claim or an authored proposal correctly interprets the story.
- Deferred/undecided/stale targets, rejected plan dependencies, missing narration
  and broken references require explicit corrections before approval.
- Draft authoring/revision is still separate from the decision UI; rejected
  dependencies are not automatically replaced or rewritten.
- Narration still needs an authorized voice choice, real timing and audio review.
  Stickman staging/sound requirements remain available, but asset availability,
  animation capability, vertical framing and rendering remain separately gated.
- This task neither approves a real pilot nor starts the next production stage.
